- A) Layered pipeline (recommended). Each layer is small and can be tested on its own:
Resource (claims/documents) → validate input
  → HttpClient.request()

- C) Middleware chain, Koa style, with use(fn). It's very flexible, but that's speculative generality we don't need (YAGNI).

Monorepo it is. Here's the SDK structure in detail. This is design section 1.

SDK structure (packages/sdk/src)

index.ts                  ← public exports only
InsuranceSDK.ts           ← entry point; wires everything together
config.ts                 ← options, defaults, environment → baseUrl
types.ts                  ← public types: Claim, ClaimStatus, CreateClaimInput, Page<T>, Document…
errors.ts                 ← SDKError base + 4 typed errors
validation/
  rules.ts                ← enums + regexes (shared with mock server)
  validateClaim.ts        ← CreateClaimInput → fields map or ok
  validateDocument.ts     ← type / mime / size checks
http/
  Transport.ts            ← interface + NodeTransport (node:http/https)
  AuthManager.ts          ← token lifecycle
  RetryPolicy.ts          ← backoff decisions
  HttpClient.ts           ← composes auth + retry + transport + error mapping
resources/
  ClaimsResource.ts       ← create / get / list / onStatusChange
  DocumentsResource.ts    ← upload / list
  StatusPoller.ts         ← polling engine behind onStatusChange

What each unit does

InsuranceSDK is the only class partners construct. It resolves the config, builds a single HttpClient, and exposes sdk.claims and sdk.documents. It contains no logic of its own.

config.ts maps environment to a base URL (sandbox → http://localhost:4000 by default, or overridden with baseUrl; production → a placeholder URL). It applies the defaults (timeout: 30000, maxRetries: 3) and fails fast if apiKey is missing or malformed.

Transport (interface) is the only code that touches the network.
interface Transport {
  send(req: TransportRequest): Promise<TransportResponse>;
}
// TransportRequest: method, url, headers, body (JSON string | multipart stream),
//                   timeoutMs, onUploadProgress?(sentBytes, totalBytes)
NodeTransport uses node:http/https. It builds the multipart body as a stream and counts bytes as they're written, which is what makes upload progress possible. Socket errors and timeouts become NetworkError. HTTP status codes are passed through untouched, because interpreting them is someone else's job.

AuthManager owns the JWT.
- getToken() returns the cached token if it's still valid with a 60s safety margin. Otherwise it calls POST /auth/token.
- If several requests arrive while a refresh is in progress, they share one in-flight promise, so there's never more than one refresh at a time.
- invalidate() is called when a request gets a 401. The request is then retried once with a new token. A second 401, or an invalid API key, throws AuthError.

RetryPolicy is pure logic with no I/O:
shouldRetry(error|status, attempt) and delayFor(attempt) → min(base · 2^attempt, cap) + jitter. It retries on 503 and NetworkError only. It never retries 400, 401, 404 or 409. The sleep function is injectable, so tests don't actually wait.

HttpClient is the single request<T>() method that wraps the layers in order: retry loop → attach token → transport → map the status. The error mapper turns 400 into ValidationError(fields), 401/403 into AuthError, and any other non-2xx into ApiError(status, code, message).

validation/ contains pure functions returning { ok: true } | { ok: false, fields }. The resources call them before any request goes out. The mock server imports the same rules.ts, so both sides apply identical rules.

ClaimsResource / DocumentsResource are thin. Each one validates, calls http.request, and returns typed results. documents.upload accepts a Buffer | Readable | string (path), works out the size and MIME type, and converts byte progress into onProgress(percent).

StatusPoller: onStatusChange(id, cb, { intervalMs = 5000 }) fetches the claim at each interval and calls cb(newStatus, claim) only when the status has changed. It returns unsubscribe(). Transient errors during polling are retried internally and don't stop the polling. An onError option reports any errors that remain after the retries.

Request flow example: claims.create(input)

validateClaim(input) ──fail──▶ throw ValidationError (no network)
        │ok
HttpClient.request(POST /claims)
  attempt 1: token ✓ → transport → 503  → RetryPolicy: wait ~200ms
  attempt 2: token expired → refresh → transport → 201 ✓
        ▼
return Claim (typed)

Errors (errors.ts)

SDKError is the base class, with code and requestId?. ValidationError adds fields. AuthError. NetworkError adds cause and retryable. ApiError adds status and body. Every error sets name correctly, and instanceof keeps working after transpiling.

❯ How does the SDK handle multiple simultaneous calls when the token has expired?

The SDK uses single-flight refresh: however many calls run at once, at most one token request is in flight at a time. Writing this out turned up a gap in the spec, which I describe at the end.

Case 1: the SDK already knows the token has expired

AuthManager stores the token's expiresAt time. It treats a token as expired 60s before that, so expiry shouldn't happen mid-request.

t=0  claims.get('A') ─┐
t=0  claims.get('B') ─┼─▶ getToken(): cached token expired
t=0  claims.list()  ─┘        │
                              ├─ first caller: no refresh in flight
                              │    → refreshPromise = POST /auth/token
                              ├─ 2nd, 3rd callers: refreshPromise exists
                              │    → await the same promise
                              ▼
                     1 token request → all 3 resume with the new token

In code:

getToken(): Promise<string> {
  if (this.token && this.token.expiresAt - 60_000 > this.now()) return Promise.resolve(this.token.value);
  this.refreshPromise ??= this.fetchToken().finally(() => { this.refreshPromise = undefined; });
  return this.refreshPromise;
}

- If the refresh succeeds: every waiting call resumes with the same new token.
- If it fails with a 503 or network error: the refresh is retried with backoff, and the waiting calls keep waiting on the same promise.
- If the API key is invalid: every waiting call gets the same AuthError. finally clears the in-flight promise, so later calls can try again instead of being stuck with a cached failure.

Case 2: the server rejects the token first (the gap)

Sometimes the server returns 401 TOKEN_EXPIRED while the SDK still thinks the token is valid. That can happen through clock skew or a mock server restarted with a new secret. Here the spec currently says invalidate() "clears the cache", and that alone isn't safe:

A, B, C all send with token T1 → all get 401
A: invalidate() → refresh → T2 stored
B: invalidate() → clears T2 (!) → refresh again → T3
C: invalidate() → clears T3 (!) → refresh again → T4

That's three refreshes when one would do, and the refreshes keep throwing away valid tokens.

Proposed fix: compare the failed token before clearing anything. invalidate(failedToken) clears the cache only if the cached token is still the one that failed:

invalidate(failedToken: string): void {
  if (this.token?.value === failedToken) this.token = undefined;
}

Each request records which token it sent, and on a 401 calls invalidate(thatToken) and then getToken():
- A: T1 is still cached, so A clears it and starts the single-flight refresh.
- B and C: if T1 is still cached, they clear nothing and join A's refresh. If the new token T2 is already stored, invalidate does nothing and getToken() returns T2 straight away.
- Result: one refresh, and A, B and C each retry once with T2. If that retry also gets a 401, the call throws AuthError. This keeps the existing "one re-authentication per request" rule, so it can't loop.

Tests this adds

- 3 concurrent calls with an expired token → exactly 1 call to /auth/token.
- 3 concurrent calls that all get a 401 → exactly 1 refresh, and all 3 succeed on retry.
- The refresh fails with an invalid API key → all 3 calls reject with AuthError, and the next call tries to refresh again.

❯ Token lifetimes of 60 seconds or less make every request fetch a new token
  Explain the issue and propose a solution, i will review it before implementation

  Searched for 2 patterns, ran 1 shell command

The issue

The SDK starts refreshing a token 60 seconds before it expires (packages/sdk/src/http/AuthManager.ts:8, :26):

const REFRESH_MARGIN_MS = 60_000;
if (this.token && this.token.expiresAt - REFRESH_MARGIN_MS > this.now()) return cached;

That works for the 1-hour tokens the spec describes. But if the server issues a token that lives 60 seconds or less, the token is already inside the refresh window when it arrives. The cached token is never reused:

┌─────────────────────────────────────────────────────────┬─────────────────────────────────────────────┐
│                     Token lifetime                      │    How long the cached token gets reused    │
├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────┤
│ 3600 s (default)                                        │ 3540 s                                      │
├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────┤
│ 65 s (the value our README suggests for trying refresh) │ 5 s                                         │
├─────────────────────────────────────────────────────────┼─────────────────────────────────────────────┤
│ 60 s or less                                            │ never: every call fetches a new token first │
└─────────────────────────────────────────────────────────┴─────────────────────────────────────────────┘

What a partner sees:
- Double the traffic: every API call costs two round trips (token, then the real request).
- Double the latency: on the mock, each request waits for an extra 200–500 ms delay.
- More random failures: with chaos on, each call has two chances to hit a 503 instead of one.
- Still correct: requests succeed, so nothing visibly breaks. That's why I graded it Minor.

The 60 seconds of headroom isn't needed for correctness anyway. If a token expires mid-request, the server answers 401, and the SDK already refreshes and retries once.

Proposed fix

Scale the margin with the token's lifetime: margin = the smaller of 60 seconds and 10% of the lifetime. Work out the refresh time once, when the token arrives.

const MAX_REFRESH_MARGIN_MS = 60_000;
const REFRESH_MARGIN_RATIO = 0.1;

// in refresh():
const lifetimeMs = expiresIn * 1000;
const marginMs = Math.min(MAX_REFRESH_MARGIN_MS, lifetimeMs * REFRESH_MARGIN_RATIO);
this.token = { value: accessToken, refreshAt: this.now() + lifetimeMs - marginMs };

// in getToken():
if (this.token && this.now() < this.token.refreshAt) return cached;

┌────────────────────────┬──────────────────────┬─────────────────────────────┐
│     Token lifetime     │        Margin        │         Reused for          │
├────────────────────────┼──────────────────────┼─────────────────────────────┤
│ 3600 s                 │ 60 s (same as today) │ 3540 s                      │
├────────────────────────┼──────────────────────┼─────────────────────────────┤
│ 65 s                   │ 6.5 s                │ 58.5 s                      │
├────────────────────────┼──────────────────────┼─────────────────────────────┤
│ 30 s                   │ 3 s                  │ 27 s                        │
├────────────────────────┼──────────────────────┼─────────────────────────────┤
│ 0, negative or invalid │ none                 │ never cached, same as today │
└────────────────────────┴──────────────────────┴─────────────────────────────┘

Why 10%:
- What the margin covers: the margin only needs to cover the time a request spends in flight. Clock differences between the partner and the server don't matter, because the expiry time is measured on the partner's own clock from when the token arrives.
- Why it's safe: 10% leaves a few seconds even for very short tokens, and the existing 401 retry covers anything that slips through.
- No change by default: for the default 1-hour token, behavior stays exactly as it is now.
- No new option: nothing changes in the SDK's public API.

The issue

Spec §4.4 (lines 250–252) says:

▎ Uploads from a non-replayable stream source are not retried, including the 401 re-auth retry… The SDK obtains a fresh token before starting a stream upload to minimise this.

The first half is built. The second half isn't. In HttpClient.request (packages/sdk/src/http/HttpClient.ts:68), a stream upload takes the cached token like any other request.

Why it matters for streams:
- The usual safety net doesn't apply. For other requests, if the server rejects the token with a 401, the SDK fetches a new token and resends the request (line 84). A stream upload can't be resent, so a 401 goes straight to the caller as an AuthError.
- The partner can't retry either. When the server answers early, the SDK destroys the source stream. To try again, the partner has to open the stream again (for example, from object storage).

When this happens in practice:
- Expiry: the cache already refreshes before tokens expire on our clock, and the server checks the token when the upload arrives, not when it finishes. So an expiring token isn't the realistic cause.
- The real gap: the server stops accepting a token the SDK still thinks is valid. Examples: the server restarts with a new signing secret, revokes tokens, or rotates keys. A long-running partner process that holds a token for up to an hour is exposed to all of these.

It's a narrow case, but when it happens the upload fails in a way the partner can't simply retry.

Proposed fix

Before a stream upload, always fetch a new token instead of using the cached one. Then the token is only milliseconds old when the upload starts.

1. AuthManager.getToken({ forceRefresh?: boolean }):
   - With forceRefresh: true, skip the cache and refresh.
   - It goes through the existing single-flight logic. If a refresh is already running, the call joins it, so 5 stream uploads at once still cost 1 token request.
   - Requests already using the old token are unaffected, because that token stays valid.
2. HttpClient.request: if the body is a non-replayable multipart (only stream uploads), call getToken({ forceRefresh: true }). Paths and Buffers keep using the cache, since they can already re-authenticate after a 401.
3. Order matters: the token is fetched before the stream is read. If the token request fails, it's retried like any token request. If it still fails, the upload is never sent and the stream is left unread, so the partner can retry with the same stream.

Cost: one extra token round trip per stream upload, about 200–500 ms on the mock. Uploads from file paths and Buffers don't change.

What it doesn't fix: a stream upload that hits a chaos 503 still fails without a retry. That's by design (the stream can't be replayed), and the README already says to buffer the stream or write it to a temp file if you need retries.

What a partner gets:
- A misleading error. A wrong size comes back as a network timeout (30 s by default) with requestSent: true. That says "the server may have stored this", which sends the partner looking at their network instead of their own input.
- Wrong progress. Progress reports go past 100% or stop early.
- A bypassed size limit. The 10 MB check runs on the declared size. A stream that declares 1 MB but sends 50 MB passes it, so only the server can catch it.
- Changing files. The same thing can happen with a file path, if the file changes size between the SDK checking its size and reading it (for example, a file still being written).

Proposed fix

Count the file's bytes while they're sent, and stop the upload the moment they don't match the declared size. The check goes in buildMultipart (packages/sdk/src/http/multipart.ts), so it covers streams, paths and Buffers.

let received = 0;
for await (const chunk of file.open()) {
  received += chunk.length;
  if (received > file.size) throw sizeMismatch(file.size, 'more');   // before sending the extra bytes
  yield chunk;
}
if (received < file.size) throw sizeMismatch(file.size, received);    // before the end of the form
yield epilogue;

1. Error type: throw ValidationError with fields.size, for example "declared 500 bytes, but the stream provided more" or "declared 2000 bytes, but the stream provided 1000". A wrong size is the caller's input error, not a network fault, and partners already handle ValidationError field by field.
2. Transport (packages/sdk/src/http/Transport.ts:135): when the source stream fails with an SDKError, pass that error through instead of wrapping it in NetworkError. The request is aborted as it is today.
3. No retries: ValidationError is never retried, which is correct for both bad input and a file that changed.
4. No partial document: the upload is aborted before the end of the form is sent, so the server never receives a complete form and stores nothing. The partner can safely fix size and upload again. I'll check this against the mock server in an end-to-end test.

What the partner gets instead: an immediate ValidationError naming the mismatch, instead of a 30 s timeout. Progress can never pass 100%, and a stream can't send more than the 10 MB limit, because sending stops at the declared size.
